Tokuchu Architecture

System context: who and what interacts with Tokuchu, and what each relationship carries.

Inside the app

Internally, Tokuchu has two halves that share a data layer but otherwise don't know about each other.

RSVP site

The attendee-facing half. Handles event creation, the invite link, RSVP collection, approval, and the survey. Survey questions are AttributeDefinition rows; answers are AttributeValue rows. Everything lives in an in-memory store. This half has no knowledge of Shopify.

Shopify side

The procurement half. Searches products across Shopify stores via WebMCP, ranks them, manages carts and checkouts, and serves the MCP endpoint that vendor agents call into. A curation agent (OpenAI Agents SDK) interprets the organizer's search intent; the actual search and ranking are deterministic.

The manifest — the bridge

The single point where the two halves meet. The RSVP site writes survey answers. The Shopify side never reads those values directly. The manifest resolves each guest's answers through variant mapping and personalization transforms into one row per recipient — and that resolved row is the only thing the cart agents, the MCP endpoint, and any vendor ever see.

Stagehand browser-agent runtime

Stagehand is the browser integration layer in agent handoff mode. It is not a source of procurement data and it does not encode the product workflow. It launches and wraps the Chrome browser context, keeps Tokuchu and Customworks open as separate pages, and exposes the native WebMCP tools registered by each page to the agent runtime.

scripts/agent-run.mjs launches local Chrome through localBrowser.launch, creates Stagehand around that browser, initializes the demo session, and passes the resulting browser context to src/agent/agent-run.ts. The runtime deliberately exposes only five generic controls to the model:

open_pageOpens a URL in the shared Stagehand browser context and assigns the tab an ID.
list_webmcp_toolsCalls Page.tools() and returns each registered tool's name, description, input schema, and frame ID.
call_webmcp_toolResolves a discovered tool by page and frame, invokes it with structured input, waits for completion, and normalizes WebMCP content and errors.
switch_tabChanges the active Stagehand page so the agent can move between Tokuchu state and the storefront.
record_checkoutUses the checkout URL captured by the runtime to call Tokuchu's post_update; the raw URL is withheld from the model.

The business operations are therefore not hard-coded as agent tools. The model discovers names such as get_customization, get_fulfillment_manifest, and add_customized_to_cart from the page where they are registered, reads their current schemas, and calls them through the generic Stagehand adapter. This lets either website change the capabilities it exposes without requiring a new agent wrapper for every function.

With TOKUCHU_STATIC=1, Tokuchu omits its server-side storefront actions, including product search, vendor handoff, and approval-driven cart work. That makes the browser agent the explicit bridge between the two sites. The runtime records every model decision, browser-tool call, WebMCP result, and final outcome under tests/videos/agent-run-*.json. The separate npm run agent-playbook path is a deterministic Playwright fallback: it uses the WebMCP polyfill and a fixed sequence, whereas the Stagehand runtime discovers and chooses calls dynamically.

The flow

1. Create and publish — the organizer builds the event and publishes it, minting the invite link. RSVP side only.

2. Configure merchandise — the organizer searches Shopify stores via WebMCP, picks a product, and the product's personalization schema becomes the survey. Shopify side only.

3. Collect answers — attendees open the invite link and fill the survey. Each answer is stored as an attribute value. RSVP side only.

4. Send to vendor — the manifest resolves answers into vendor rows. Tokuchu calls create_cart at the shop via WebMCP. As more RSVPs arrive, quantities stay current. This is where the two halves meet.

5. Lock and order — at the cutoff, values freeze, the manifest grades each unit (ready, incomplete, excluded), and Tokuchu creates a checkout via WebMCP.

6. Vendor reporting — the vendor's agent calls into Tokuchu's MCP endpoint with a scoped token, reads the manifest, and posts status updates.
